# Certificate Workflow - Complete Implementation & Testing Guide

## Summary of Work Completed

This document describes the complete end-to-end certificate workflow implementation that was tested and deployed on May 18, 2026. The workflow allows admins to generate certificates, club advisors to approve/reject them, and students to view approved certificates.

## Problem Statement

The certificate workflow had two critical issues:
1. Club advisors couldn't see pending certificates generated by admins (RLS policy missing)
2. When club advisors clicked "Approve", the certificate status wasn't updating in the database (RLS policy blocking update)

## Solution Implemented

### 1. Created Certificate Status Update API Endpoint
**File**: `/app/api/certificates/update-status/route.ts`

This endpoint uses the Supabase admin client (with service role key) to bypass RLS restrictions and update certificate status. Regular Supabase clients cannot perform these updates due to RLS policies.

```typescript
// The endpoint accepts:
// POST /api/certificates/update-status
// Body: { certificateId: string, action: "approve" | "reject" }
// Returns: { success: boolean, message: string, certificateId, newStatus }

// It performs:
// 1. Fetches certificate details
// 2. Updates certificate status (approved/rejected)
// 3. If approving, updates event status to "completed"
```

### 2. Updated Club Advisor Approval Functions
**File**: `/app/president/certificates/page.tsx`

Modified `approveCertificate()` and `rejectCertificate()` functions to call the new API endpoint instead of directly updating the database with the regular Supabase client.

### 3. Applied RLS Policies to Supabase Database
**Migration Source**: `supabase/migrations/20260519_certificates_rls_policies.sql`

Four policies were applied manually via Supabase SQL Editor:

#### Policy 1: Club Advisors Can Read Certificates
```sql
DROP POLICY IF EXISTS "Club advisors and presidents can read certificates" ON public.certificates;
CREATE POLICY "Club advisors and presidents can read certificates"
ON public.certificates
FOR SELECT
USING (
  auth.uid() IN (
    SELECT id FROM public.users 
    WHERE role IN ('club_advisor', 'admin')
  )
);
```

#### Policy 2: Club Advisors Can Update Certificate Status
```sql
DROP POLICY IF EXISTS "Club advisors and presidents can update certificates" ON public.certificates;
CREATE POLICY "Club advisors and presidents can update certificates"
ON public.certificates
FOR UPDATE
USING (
  auth.uid() IN (
    SELECT id FROM public.users 
    WHERE role IN ('club_advisor', 'admin')
  )
)
WITH CHECK (
  auth.uid() IN (
    SELECT id FROM public.users 
    WHERE role IN ('club_advisor', 'admin')
  )
);
```

#### Policy 3: Admin Can Insert Certificates
```sql
DROP POLICY IF EXISTS "Admin can insert certificates" ON public.certificates;
CREATE POLICY "Admin can insert certificates"
ON public.certificates
FOR INSERT
WITH CHECK (
  auth.uid() IN (
    SELECT id FROM public.users 
    WHERE role = 'admin'
  )
);
```

#### Policy 4: Students Can View Their Approved Certificates
```sql
DROP POLICY IF EXISTS "Students can read their own certificates" ON public.certificates;
CREATE POLICY "Students can read their own certificates"
ON public.certificates
FOR SELECT
USING (
  (auth.uid() = user_id AND status = 'approved') OR
  auth.uid() IN (
    SELECT id FROM public.users 
    WHERE role IN ('club_advisor', 'admin')
  )
);
```

## Key Technical Details

### Why API Endpoint Was Needed
- Regular Supabase client: Restricted by RLS policies, cannot update certificate status
- Admin client (service role): Bypasses RLS, can perform privileged operations
- Solution: Create backend API endpoint using admin client for certificate approval

### Database Architecture
- **Table**: `public.certificates`
- **Key Columns**: id, certificate_no, status (pending/approved/rejected), user_id, event_id, issued_at
- **RLS Enabled**: Yes
- **Access Control**: Via role-based policies (admin, club_advisor, student)

### Troubleshooting

**Certificate not updating when approved:**
- Check if `/api/certificates/update-status` endpoint is returning success
- Verify admin client has SUPABASE_SERVICE_ROLE_KEY in environment
- Check browser console for errors
- Verify RLS policies are applied to Supabase

**Club advisor can't see pending certificates:**
- Ensure RLS policy "Club advisors can read certificates" is applied
- Verify club advisor role is set correctly in users table
- Check `/api/certificates/pending` endpoint response

**Students can't see their certificates:**
- Verify RLS policy "Students can read their own certificates" is applied
- Certificate status must be "approved" (RLS policy requires this)
- User ID in certificate record must match authenticated user's ID
